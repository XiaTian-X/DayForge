# 部署、备份与恢复

## 支持场景

后端面向家庭局域网服务器或 NAS。初始数据库为 SQLite，应用使用单 worker。公开到广域网时必须由可信反向代理提供 HTTPS、访问控制和正确的转发头配置。

当前发布版不支持 PostgreSQL 或其他数据库。`DATABASE_TYPE` 必须为 `sqlite`；如果直接设置 `DATABASE_URL`，必须是 `sqlite+aiosqlite` URL，否则进程在启动阶段拒绝配置。逻辑归档是未来跨数据库迁移通道，不代表对应数据库已获得运行支持。

## 首个生产基线重置

本仓库在尚无真实数据和受支持旧客户端时，将 Android Room 重置为 schema `1`，将后端 Alembic 重置为 revision `000000000001`。此前的测试数据库不能升级或 stamp 到新 revision：Android 安装后会对较高的开发版 schema 执行破坏性重建；后端部署前必须停止旧服务、删除旧测试 SQLite 文件及其 `-wal`/`-shm` 伴随文件，再由 `alembic upgrade head` 创建新库。需要保留的仅是配置与密钥，旧测试备份不得恢复到本基线。

从该基线产生真实数据后，禁止再次重写 Room 或 Alembic 历史；所有结构变化必须使用经过测试的增量迁移和升级前备份。

不得在 GitHub 托管 Runner 中直接访问家庭 NAS。初期部署由 NAS 主动拉取不可变镜像；未来自动部署需要受控自托管 Runner 和最小权限凭据。

## 配置与秘密

- `.env`、JWT 密钥、管理员初始密码、真实数据库和备份不得进入 Git。
- Android release keystore 和密码离线保存至少两份；keystore 不进入仓库。
- 初始管理员凭据只用于明确的首次引导，不应长期保留在环境中。

配置字段名大小写不敏感，部署文件仍统一使用大写名称。对于同一字段，优先级为显式构造参数、环境变量、`.env`、默认值；构造参数也遵循大小写规则，不再静默忽略小写已知字段。不同来源合并后仍执行生产密钥、管理员凭据成对及强度、数据库类型/URL 校验；无效配置必须拒绝启动，不能回退默认值绕过校验。

## 镜像

发布镜像使用版本标签和 commit SHA，不复用可变的生产标签作为唯一回滚依据。目标 NAS 可能是 `amd64` 或 `arm64`，发布流水线应构建并验证所支持的架构。

## 升级

1. 验证备份可以读取并记录校验和。
2. 记录当前镜像 SHA 和 Alembic revision。
3. 停止写入或进入维护窗口。
4. 执行迁移。
5. 启动一个应用 worker并进行健康、登录和最小同步检查。
6. 确认后再恢复正常访问。

破坏性迁移必须说明旧镜像能否运行在新 schema 上。代码回滚和数据库回滚是两个独立动作，不能假定只切换镜像就能恢复。

## 恢复

恢复后端数据后必须轮换 `sync_epoch`，使终端进行受控重新同步。恢复演练至少验证账户、实体、计时、变更日志、revision snapshot 和幂等记录的一致性。

未来切换 PostgreSQL 等数据库时，先建立数据库无关的逻辑归档与导入验证；不能直接把 SQLite 文件转换视为唯一迁移方案。
