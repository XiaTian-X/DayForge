# 普通验证执行与独立审查的有限重叠

2026-11-15 经独立静审采纳为**未来全新准入的可选组织方式**。当前及历史已采用的串行准入不倒改；是否实际重叠仍由root逐批明确决定。它只减少设备空等，不改变应用安全保证、原完整类、同PID、预算、断言、失败证据或任何验收信用。

适用条件必须全部满足：

1. 同一冻结源码、schema、工具、APK、runner和profile；下一项是原已审完整普通安全单位，无要求前批已审成功的硬前序。已知修复安全门、P1/P2、C25专用顺序、UI／性能、年度／GC／Display前序及跨profile操作均排除。
2. 前批原driver实际退出0；root以原read_cases／discover核两套完整XML、精确身份、零失败/错误/跳过，核source/APK/fresh ec/实际UTP/原预算/PID事件及原日志。失败、无法解释的UNKNOWN END、owner／cleanup围栏或来源异常仍HOLD；预期负例必须对应原故障与完整末尾断言，不能用包空替代native关闭要求。
3. 下一AGP之前，root已完整保存原run、两套结果、raw/UTP/日志、所有本批强制additionalTestOutput（PNG/JSON等）、APK/ec、source/profile/build预算、admission/terminal和实际退出观察。索引叶集合/hash精确、无链接/硬链接、复制已完成；独审只读已封副本和仍冻结的源码。审查或exporter仍依赖可变build产物且来源等价未闭合时，不适用。
4. root实际确认原host、测试PID及隔离包已释放；下一批仍重新核设备、唯一owner、时钟/日界、内存和原预算，紧靠Popen复核日界。只有root一个设备/构建执行owner及原全程锁；另一个审查者仅轻量只读，不运行ADB/JVM/Gradle/Docker/采样或大内存处理。
5. 每次Popen最多一个前批待独审。后批若先结束，先封存并停止第三批，先完成旧审再审新终态；不形成待审队列或第二并行审查。独审未决/失败不恢复准入资格：后续启动前须明确依赖与共享资源风险，无法判断保持HOLD。已在途、确实独立且守卫正常的普通批可安全完成，不粗暴中断END/Job，也不活动改源或以新绿结果抵消前批问题。
6. JUnit原始结果照实保存，验收状态仍为待独审。完整独审前不得填写reviewed capture、成功映射、P1/P2输入或最终通过账；P1/P2及任何硬前序继续等齐完整安全证据和独立准入。

新准入须明确引用本规则、适用性判断、前批机械就绪/完整封存/实际释放、待审事实、本批完整范围/source/profile及新鲜预算等证据。只改status不能启动；不新增执行器、调度器或自动连跑。当前实际执行若没有产生重叠，也不记成试验收益。

750的真实PNG说明通用raw/results/coverage归档未必涵盖AGP附加输出。必须按实际测试合同补齐并纳入最终索引；缺件或来源不明时停止后续，不能拿旧run/其它variant画面代替。PNG字节有效、实际画面和人类操作时延分别验收。

验证收益时记录前批终态、封存/机械就绪/释放、独审完成和下一Popen的真实时间。旧样本只有约4–6分钟审查尾可被覆盖的潜力，尚无并行净收益结论；不保证每批5–10分钟，不视为应用性能改善。出现资源竞争、原件缺口或待审积压即回到原串行顺序，不放宽期限或改判失败。

重叠执行只适用于事前声明的独立单元。结果归属和失败保留遵循[普通验证规范](../TESTING.md)与[进程恢复准入](../PROCESS_RECOVERY_TESTING.md)。
