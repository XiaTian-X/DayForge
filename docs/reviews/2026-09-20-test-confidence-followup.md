## 已确认的问题及修补

### P2：计时持久化只检查时长下界，错误放大仍能通过

原 `TimerServicePersistenceTest` 等待真实 61 秒后仅断言 `durationSeconds >= 60`，然后将读取出的记录
与重开连接后读取的同一记录比较。把 `handleStop` 的秒数乘以 60（仍经过安全上限）后，三个现有服务
测试全部通过，构建和运行均成功。这是实际运行的漏检，不是根据代码推测。

补强同一完整状态机用例：在 start/pause/resume/stop 调用前与提交确认后记录独立单调时钟，形成两个
实际运行区间的上下界；暂停重建后真实等待 5 秒、恢复后运行至少 1.1 秒，验证暂停状态和已累计时长保留。
最终秒数和毫秒数必须落在独立范围内，秒/毫秒换算、stop 命令、区间总和和日分摊也必须一致，并重开连接
逐项核对。保留原有有效断言，不通过提高超时或修改系统时钟解决问题。

独立上下界随实际调度观测生成，不使用固定“应恰好 61 秒”的脆弱断言；不调用被测时长计算器生成预期。
真实重启/断电仍不在本次证明范围内。

### P2：统一入口没有拒绝跳过的 instrumentation 用例

此前 `verify android` 只检查 Gradle 成功和三个应用类的覆盖率校准。JUnit 被忽略的用例可能与其他正常
用例一起得到成功结果，而覆盖率校准仍能通过。上一轮 XML 的 712 项确实全部执行且零跳过，此问题不否定
已经归档的结果，但会放过后续跳过行为。

新增 XML 结果门禁，拒绝缺失/空报告、失败、错误、跳过、错误计数以及计数与 testcase 不一致的报告，接入
完整真机入口。五项主机 Python 回归覆盖正常多报告、缺失/损坏/空报告、单个报告失败、伪造零计数和无效计数。
它不声称自动证明所有业务场景或发现列表完整；仍需核对运行范围和迁移映射。

### P3：稳定文档残留迁移前验收措辞

修正“剩余历史测试”“Robolectric 覆盖 API 26/29/35”和 Retrofit 尚未真机执行的过时说明。
当前证据明确限于 API 35，历史 API 列表不扩大成多版本真机验收。

## 排除的疑点与证据边界

- 组件状态测试由测试代码传入 habit ID，本身不能证明绑定读取；另有 `WidgetRefresherTargetsTest` 从生产
  刷新入口检查实际偏好值、最新绑定和不同类型隔离，因此没有把该单测局限误报成整组测试缺失。
- `runCatching` / `catch` 用例检查具体异常类型、身份或显式 `fail`，未发现本次新增恒真占位或吞异常取绿。
- 同步 fixture 的 HTTP 响应模拟只证明客户端请求和本地持久化；后端 runtime fixture 使用真实生产会话及
  Alembic 数据库、独立连接与延迟外键 COMMIT 故障，二者仍不等于 NAS/真实部署联合验收。
- 数据库规则限制在 `com.dayforge.testbed`，主要 DataStore 使用独立文件并取消/等待 scope；实际桌面、其他
  Android API/OEM、进程被杀/断电及网络组合沿用最终报告的环境豁免。
