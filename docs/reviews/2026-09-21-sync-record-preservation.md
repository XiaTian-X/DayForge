# 同步合并的关联记录保留（#169）

## 问题与证据

#157 联合真机验收发现倒计时完成状态在同步后消失，重试产生
`ACTIVE_TIMER_EXISTS` 和 `TIMER_NOT_FOUND`。服务端审计中，旧习惯删除及同名新习惯创建均成功；
新倒计时有已接受的 start，却没有对应 stop，后续不同 session 的 start 被未结束会话阻塞。
设备仍保存后续一次完整计时及被拒绝的 start/stop。

Android 六类实体的同步 DAO 使用 `INSERT OR REPLACE`。对习惯、指标和计时记录执行替换，
会触发真实 SQLite 外键级联删除：运行中/已完成计时、打卡、指标记录、关联或计时区间丢失。
同步抑制 outbox 期间，这些连带删除不会产生补偿命令。服务端已接受的 start 因而可能成为孤立会话。

新增真机回归先在未修复代码运行：6 项存储合并测试中 5 项失败，分别观察到计时记录为 null、
指标记录为 null、计时区间为空和同名不同身份未拒绝；明确删除后同名重建通过。
另一个真实计时服务测试也在合并后观察到活跃记录为 null（1 项失败），不是只用 mocked DAO 推断。

## 修复边界

- 六类同步实体按照合并器已解析的本地主键原位 UPDATE；新增使用 INSERT OR ABORT。
- 更新必须恰好影响一行；已解析但消失的本地 ID 不能被当成新实体插入。
- 同名不同 UUID、不同 UUID 的同一习惯/指标关联冲突，不再静默替换另一实体。
- 继续沿用整页 Room 事务及 outbox 抑制；失败回滚整页，明确删除仍按原逻辑传播。
- 不更改协议字段、Room schema、后端、依赖、计时状态机或 UI/UX。
- 此修复不自动恢复已经级联删除的历史本地记录，也不按墙上时间补造计时完成事实。

## 回归覆盖

`SyncMergeRecordPreservationTest` 覆盖父记录重复合并、运行中及已完成计时、区间/分摊、
待同步命令、指标记录和关联保留，叶子实体重复合并的主键稳定，唯一键冲突、整页回滚、
SQL 更新失败后重开与重试、缺失目标 ID 拒绝，以及显式删除后同名不同 UUID 重建。
存储测试的人工事实仅为 FK/持久性夹具，不作为计时服务完成的证据。

`TimerServicePersistenceTest.countdownSurvivesParentSyncAndAutomaticallyQueuesOneStop`
从真实系统服务开始一分钟倒计时，在运行时合并两次服务器习惯变化；真实等待到时后断言
只有同一 session 的 start/stop、60 秒完成值、60,000 毫秒区间/分摊，完成后再合并仍保留记录。

  0 失败、0 错误、0 跳过；比基线增加 10 项。构建耗时 12 分 58 秒，lint、编译警告预算
  （0/0）和覆盖率校准通过。根检查 17 项通过。
- 测试包与人工验收包隔离；未清除验收账户或数据库。
- 用户明确授权后，通过正常 API 取消本次特定残留会话；使用原控制设备身份及最新 revision、
  sequence、generation 校验，没有创建完成事实。只读比对确认其余计时会话和八类业务表逐行摘要不变，
  服务端没有剩余活跃计时。随后用户显式重试手机保留的命令，同步成功且完成记录保留。
- 旧代码失败 XML、针对性通过 XML、完整结果及受控恢复脚本保留在仓库外临时证据目录；

- 用户联合复测已通过：拒绝命令恢复后重复同步/重开正常；新建一分钟倒计时后立即开始、
  运行中同步及完成后重开正常，目标归属正确；指标改名后原记录与瞬时时间保留。
- 拔掉 USB 后离线 start/pause/resume/stop、录入指标并重开保留，恢复转发后两次同步无重复、
  无计时问题。服务端确认同一会话四条命令均 applied，最终 completed、60,000 毫秒且有完成事实，
  无活跃残留。证据：[第三组](https://github.com/XiaTian-X/DayForge/issues/157#issuecomment-5761315342)、
  [第四组](https://github.com/XiaTian-X/DayForge/issues/157#issuecomment-5761406089)。
- 本轮网络路径为 USB 转发，不能等同于真实 LAN/WAN/VPN 或完全无网验证。
  自然跨午夜、系统重启、第二终端接管、外网/NAS 仍由 #21/#157 跟踪，小组件按用户决定延期。
