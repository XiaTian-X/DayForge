# 计数、指标与目标进度的本地命令与读取合同

DayForge 在已登录且有权限的设备上通过 Room/SQLite 保存日常操作，离线时仍能使用核心功能。网络接纳、必要提示、目标进度和历史明细分别有自己的来源与完成条件。计数增加或撤销的链路覆盖原输入、业务事实与 outbox、真实 ACK、卡片与首页，以及需要用户录入的关联指标。打卡、计时、一次性任务和独立指标沿用各自的业务规则，共用数据库生命周期、可信读取与结果交付机制。[同步协议](../SYNC_PROTOCOL.md)

## 谁可以读取、提交和发布

设备长期绑定账户可保留已验证的本地状态。同一账户在多设备上使用时，每个安装拥有自己的会话、设备权限、副本和密钥；主设备可按既有协议变更。页面输入绑定原账户、会话代次、数据库实例和目标对象。退出、重新登录、撤权、恢复或数据库重开会使相应旧输入和发布资格失效。网络回复归属原请求和设备。权限版本、恢复围栏和来源变化均须重新判断。[数据库图与生命周期](../../android/app/src/main/java/com/dayforge/data/local/DatabaseRuntimeHost.kt)

入口以及提交前保留新鲜鉴权，并保护最后检查到事务实际结束或结果发布的边界。锁外纯计算只使用冻结输入，回到事务重验依赖。证明有效才可重用已验证的业务结果。当前信任边界为受控应用、OS 和 Keystore；没有新增强制联网、新设备继承别台设备权限或整库同时回滚检测的保证。

自动初始化设备主题会写入会话准备读取的同一份本机偏好。准备与初始化同时发生时，等待方先释放账户锁，取得所需资源后才开始读取快照。物理事务、会话校验和准备结果发布保留原边界。用户主动修改主题或切换账户仍可使旧快照失效，旧操作保持拒绝，显式重试只重新准备会话。

## 计数增加到必要指标

| 边界 | 持久事实与对用户的含义 |
| --- | --- |
| T0 命令准备 | 为支持恢复的命令记录稳定身份、原对象与输入。UI 可以表达正在处理。计数、指标值和 outbox 尚不能仅依据准备记录报为已保存。 |
| T1 可靠保存 | 在受控事务内验证实际业务依赖和写集合，写入业务事实与对应 outbox，记录命令结果。以实际事务结束为准。UI 返回同一命令的已证结果。 |
| T2 结果交付 | 有资格的消费者使用原回执与结果完成交付。新用户输入是独立命令，例如确认关联指标值。其 T1 已保存而 T2 待完成时，继续交付沿用原指标回执。 |
| 后台 ACK | 本地接纳校验原请求、传输、受影响对象、后继、权限与实际写入，原子维护回执、影子与队列。响应丢失可幂等重放，前台保存状态与服务器同步状态分别表达。 |

取消、真实事务结束异常或进程终止时保留未知结果。恢复按原命令身份检查持久回执、效果、outbox 与依赖，禁止把超时当作回滚或以新命令重复写入。关闭必要提示表示稍后处理。只有完整证据确认已保存计数的后续处理因合法变化失去资格，用户明确要求结束且提交前复核通过，才可结束该后续处理。保留原事实；证据缺失、损坏和未知提交继续走恢复。独立指标命令的显式结束另须符合其准备状态及完整无效果证明。[命令存储](../../android/app/src/main/java/com/dayforge/data/repository/CountCommandStore.kt) · [恢复流程](../../android/app/src/main/java/com/dayforge/domain/service/CountCommandRecoveryWorkflow.kt)

## 哪些结果可以复用

持久根和成员目录绑定数据身份、验证规则及覆盖范围。计数计算块按对象、轮次与业务日所属月份组织；已封存块可重用原结果，活跃块可从上次已提交的结果推进。撤销、回填、跨日变化、同步后继和删除可能影响多个块。成员存在、应当缺席的成员、来源关系及原始字节内容都属于相应证明范围。正式写入、后台合并与恢复应维护相关依赖，或撤销资格并由完整验证重新建立。没有已维护证据的业务路径继续原验证。[可信内核](../../android/app/src/main/java/com/dayforge/data/repository/CountTrustKernel.kt) · [计算块](../../android/app/src/main/java/com/dayforge/data/history/CountCalculationBlocks.kt)

常用摘要和明细使用不同读取合同。卡片和首页共享同一快照时，发布必须覆盖完整快照；必要提示还须证明其来源与当前资格。独立指标详情的列表首屏和完整趋势图仍有不同的输入要求。API/实现要求完整历史或同日期完整组时，分页、单个叶子、日期聚合或“最新节点”均不能代替原完整证据。受到支持的暖读与 ACK 可按相关范围验证；缺钥、坏认证、旧范围或额外效果必须显式处理。正常同设备重开、首次建证和换设备重建分别验收，记录未命中与重建开销。[指标展示读取](../../android/app/src/main/java/com/dayforge/data/repository/MetricDisplayReader.kt)

打卡保留原完成与撤销语义，计时结果只能来自完整状态机及跨业务日分配。一次性任务保留版本/head CAS 与撤销来源。目标保持单父节点和防循环，指标仍可独立录入或经已验证的关联提示录入。本地持久时间为 UTC 瞬时，业务日由记录时的 IANA 时区决定。迁移、旧格式、恢复和 Account/Host 切换都须保留原始数据归属与拒绝条件。[架构](../ARCHITECTURE.md)

## 怎样判断可以交付

真实交互分别记录首个可见反馈、可靠保存、正确结果与必要提示、下一次允许操作、同步完成和积压收敛。家庭场景以多习惯、每日少量使用及长期跨日积累为主。历史中的 8/80 指开始测量前已存在的记录数。同日大量计数、连续输入、后台 ACK 竞争、正常重开和恢复分别报告。100 ms 反馈/返回、500 ms 本地保存/本地 ACK、700 ms 结果/提示、150 ms 暖资源占用、2 秒冷首次可操作是原项目预算。保留原失败、设备、配置和计时边界，分别报告安全、产品体验与内部归因。

允许带真实反馈、可安全继续操作且最终收敛的个位数秒等待。保持控件位置、清楚表达重复输入未接纳、已保存待交付和待同步。自然交互可提前准备输入，确认时重新鉴权并检查依赖，取消可丢弃准备。不能用固定动画、骨架或延迟成功提示代替可操作性、实际帧、可靠保存及恢复验收。当前执行范围与缺项见[验证摘要](../reviews/refactor-verification.md)。
